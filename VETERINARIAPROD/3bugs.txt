SECCIÓN 1 — AUTENTICACIÓN Y SESIONES (servicio auth)
────────────────────────────────────────────────────────────────────────────────

[BUG-001] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : Se usaba `logger.warn(` en 4 lugares del controlador pero la
               variable importada se llama `log`, no `logger`. Cualquier llamada
               a ssoConnect o ssoCallback crasheaba el proceso con
               "ReferenceError: logger is not defined".
  QUÉ SE HIZO: Reemplazo masivo de todas las ocurrencias logger. → log. con
               replace_all.

[BUG-006] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : El endpoint POST /auth/2fa/challenge no verificaba si el código
               TOTP ya había sido usado. Dos requests paralelas con el mismo
               código válido podían autenticarse simultáneamente (race condition).
  QUÉ SE HIZO: Implementación del patrón "burned token" con Redis SET NX EX 90.
               El primer request quema el código; el segundo recibe 401 aunque
               el código sea matemáticamente válido.

[BUG-007] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : Tras completar el desafío 2FA, el pending token (JWT de corta
               duración emitido durante el login) nunca se revocaba. Podía
               reutilizarse hasta su expiración natural para abrir nuevas
               sesiones sin contraseña.
  QUÉ SE HIZO: Después de verificar el TOTP exitosamente, se extrae el JTI del
               pending token y se inserta en Redis con `revoked:{jti}` y TTL
               igual al tiempo restante del token.

[BUG-008] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : El secreto TOTP (two_factor_secret) se almacenaba en texto plano
               en la tabla users. Un atacante con acceso de lectura a la BD
               podía clonar los autenticadores de todos los usuarios.
  QUÉ SE HIZO: Al guardar el secreto se cifra con shared/encryption.js
               (AES-256-GCM). Al leer para verificar se descifra. Afecta los
               3 flujos: setup (POST /2fa/setup), verificación (POST /2fa/verify),
               desactivación (DELETE /2fa) y challenge (POST /2fa/challenge).

[BUG-010] services/auth/src/controllers/auth.controller.js (pending tokens)
  QUÉ PASABA : El pending token para 2FA no tenía revocación de JTI al
               completar el flujo, permitiendo replay en la ventana de
               expiración.
  QUÉ SE HIZO: Ver BUG-007 — misma corrección.

[BUG-013] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : Las API keys no validaban sus scopes contra una lista de valores
               permitidos. Un scope arbitrario podía ser emitido.
  QUÉ SE HIZO: Validación de scopes contra Set ALLOWED_API_KEY_SCOPES antes
               de persistir la clave.

[BUG-014] services/auth/src/controllers/auth.controller.js
  QUÉ PASABA : La fecha de expiración de API keys no tenía límite máximo. Se
               podían crear claves con expiración de 100 años.
  QUÉ SE HIZO: La fecha de expiración se capea a máximo 1 año desde la creación.

[BUG-015] services/auth/src/routes/auth/public.routes.js
  QUÉ PASABA : El endpoint POST /password-reset/confirm no tenía rate limiting.
               Un atacante podía probar tokens de reset por fuerza bruta de
               forma ilimitada.
  QUÉ SE HIZO: Añadido passwordResetConfirmLimiter: máximo 5 intentos por hora
               por IP usando express-rate-limit.

               Transcurrido ese tiempo se vuelve a consultar el discovery.

SECCIÓN 3 — AUTORIZACIÓN Y ROLES (shared/requestContext.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-16] shared/requestContext.js
  QUÉ PASABA : Los roles extraídos del header x-user-roles se aceptaban sin
               validación. Un atacante que pudiera manipular el header (o un
               bug en el gateway) podía inyectar roles arbitrarios como

SECCIÓN 4 — FIRMA INTERNA DE SERVICIOS (shared/internalAuth.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-1] shared/internalAuth.js — Replay de firma HMAC
  QUÉ PASABA : La firma HMAC interna entre microservicios no tenía protección
               contra replay. Un atacante que capturara un request firmado
               podía re-enviarlo indefinidamente.
  QUÉ SE HIZO: Implementación de nonce store en Redis con SET NX. Cada firma
               incluye un nonce único que se "quema" al primer uso. Intentos
               de replay retornan 401 y quedan logueados.

[BUG-21] shared/internalAuth.js — Information disclosure en 401
  QUÉ PASABA : Las respuestas 401 de internalAuth incluían el campo `reason`
               con detalles del motivo de rechazo (signature mismatch, expired,
               replay detected). Esto ayuda al atacante a calibrar sus ataques.
  QUÉ SE HIZO: El campo `reason` se eliminó del cuerpo de respuesta HTTP.
               El motivo real solo se registra en el log interno.

SECCIÓN 6 — SSRF (shared/ssrf.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-4] shared/ssrf.js — IPv6 scope IDs y direcciones mapped
  QUÉ PASABA : La función isPrivateIpv6 no eliminaba los scope IDs de IPv6
               (ej: ::1%eth0) antes de evaluar si la IP era privada. Tampoco
               detectaba las IPv4-mapped en IPv6 (::ffff:127.0.0.1) como
               privadas.
  QUÉ SE HIZO: Se extrae y descarta el scope ID antes del análisis. Para
               ::ffff: se extrae el IPv4 embebido y se evalúa con isPrivateIp.

[BUG-7] shared/ssrf.js — IPs en notación decimal
  QUÉ PASABA : validateUrl no detectaba IPs en notación decimal (ej:
               2130706433 = 127.0.0.1 o http://0x7f000001). Un atacante podía
               bypasear la lista negra de IPs privadas.
  QUÉ SE HIZO: Detección de strings que sean enteros puros: se convierten a
               notación dotted y se evalúan con isPrivateIp.

SECCIÓN 8 — GDPR / DERECHO AL OLVIDO (shared/gdpr.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-20] shared/gdpr.js — anonymizeClient incompleto
  QUÉ PASABA : La función anonymizeClient anonimizaba los datos del cliente en
               la tabla clients pero no limpiaba: sesiones activas del portal
               (portal_sessions), datos médicos sensibles en tele_sessions
               (chief_complaint, notes) ni payloads de notificaciones pendientes
               (notification_retry_jobs).
  QUÉ SE HIZO: Añadidas tres operaciones de limpieza:
               1. DELETE FROM portal_sessions WHERE client_id = :cid
               2. UPDATE tele_sessions SET chief_complaint=NULL, notes=NULL
               3. UPDATE notification_retry_jobs SET payload_json='{}' para
                  jobs del cliente en esa org.

[BUG-22] shared/gdpr.js — Sin atomicidad transaccional
  QUÉ PASABA : Las ~7 operaciones de anonymizeClient se ejecutaban como queries
               independientes. Si la conexión fallaba a mitad del proceso, el
               cliente quedaba parcialmente anonimizado (algunos datos borrados,
               otros intactos). Estado inconsistente e inauditable.
  QUÉ SE HIZO: Todo el bloque de anonimización envuelto en db.transaction().
               Si cualquier paso falla, toda la operación hace rollback y el
               estado del cliente permanece intacto.

SECCIÓN 9 — CADENA DE AUDITORÍA (shared/audit.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-17] shared/audit.js — Fallback de AUDIT_CHAIN_SECRET
  QUÉ PASABA : getAuditSecret() tenía fallbacks: AUDIT_CHAIN_SECRET →
               FIELD_ENCRYPTION_SECRET → JWT_SECRET. Comprometer el JWT_SECRET
               (que protege tokens de usuario) automáticamente comprometía
               también la integridad de la cadena de auditoría, permitiendo
               a un atacante forjar entradas de auditoría sin detección.
  QUÉ SE HIZO: Los fallbacks eliminados. Solo se acepta AUDIT_CHAIN_SECRET.
               Si no está configurado, se lanza un error explícito que impide
               el arranque del servicio.

SECCIÓN 10 — REINTENTOS DE NOTIFICACIONES (shared/notificationRetry.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-34] shared/notificationRetry.js — Sin timeout en ejecución de jobs
  QUÉ PASABA : executeJob() no tenía timeout. Si un canal (email, SMS,
               WhatsApp, FCM) se colgaba o tardaba indefinidamente, el worker
               de reintentos quedaba bloqueado sin procesar otros jobs.
               Podía causar acumulación de mensajes no enviados y OOM si
               muchos workers se colgaban en paralelo.
  QUÉ SE HIZO: Envuelto en Promise.race() con un timeout configurable via
               NOTIFICATION_JOB_TIMEOUT_MS (default 30 000 ms). Si el timeout
               se dispara, el job falla con el error "Job timeout" y sigue el
               proceso de retry normal.

SECCIÓN 11 — WEBRTC / TELEMEDICINA (shared/webrtc.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-15] shared/webrtc.js — Secret hardcodeado en adaptador builtin
  QUÉ PASABA : El adaptador builtin de WebRTC tenía el fallback:
               process.env.WEBRTC_ROOM_SECRET || process.env.JWT_SECRET ||
               'vm_webrtc_secret'. En instalaciones mal configuradas, todos
               los tokens de sala se firmaban con el literal 'vm_webrtc_secret'
               público, permitiendo a cualquiera generar tokens válidos para
               unirse a consultas de telemedicina ajenas.
  QUÉ SE HIZO: Eliminados los fallbacks. WEBRTC_ROOM_SECRET es obligatorio;
               si no está configurado se lanza un Error que impide generar
               tokens, forzando la configuración correcta.

SECCIÓN 12 — GESTIÓN DE SECRETOS (shared/secrets.js)
────────────────────────────────────────────────────────────────────────────────

[BUG-27] shared/secrets.js — SECRETS_JSON en producción sin advertencia
  QUÉ PASABA : SECRETS_JSON permite pasar todos los secretos de la aplicación
               como variable de entorno en texto plano. En producción esto es
               un riesgo ya que las variables de entorno pueden ser visibles
               en logs de CI/CD, paneles de plataforma, etc.
  QUÉ SE HIZO: Añadida advertencia en consola cuando NODE_ENV === 'production'
               y SECRETS_JSON está configurado, recomendando usar SECRETS_FILE
               apuntando a un volumen montado.

[BUG-28] shared/secrets.js — Cache del bundle sin TTL
  QUÉ PASABA : Una vez cargado el bundle de secretos, nunca se recargaba
               durante la vida del proceso. En servicios de larga duración, la
               rotación de secretos (cambio de SECRETS_FILE) no tenía efecto
               hasta reiniciar el servicio manualmente.
  QUÉ SE HIZO: Añadido TTL de 10 minutos (configurable via
               SECRETS_CACHE_TTL_MS). Transcurrido el TTL, el próximo acceso
               recarga el bundle desde disco o variable de entorno.

[BUG-29] shared/metrics.js — Endpoint /metrics sin autenticación

               tokens activos, errores RBAC) sin ningún control de acceso.

SECCIÓN 14 — PORTAL DEL PROPIETARIO (services/portal)
────────────────────────────────────────────────────────────────────────────────

[BUG-001-PORTAL] services/portal/src/portal.common.js — Cuentas suspendidas
  QUÉ PASABA : portalAuth verificaba el JWT pero no consultaba si la cuenta
               del cliente seguía activa en la BD. Clientes con is_active=0
               (suspendidos o eliminados) podían seguir usando el portal
               mientras su token no expirara.
  QUÉ SE HIZO: Añadida consulta DB en portalAuth: SELECT id FROM clients
               WHERE id = :id AND is_active = 1. Si el cliente no existe o
               está inactivo, retorna 403 "Cuenta suspendida o eliminada".

[BUG-PORTAL-BILLING] services/portal/src/routes/portal.billing.routes.js
  QUÉ PASABA : Los 3 endpoints de facturación del portal (GET /, GET /:id,
               POST /:id/pay) filtraban por client_id pero no por
               organization_id. Un cliente de una org podía ver y pagar
               facturas de otra org si conocía el ID.
  QUÉ SE HIZO: JOIN con branches añadido a todas las queries con condición
               AND b.organization_id = :orgId donde orgId proviene del JWT
               del propietario.

[BUG-PORTAL-APPOINTMENTS-IDOR] services/portal/src/routes/portal.appointments.routes.js
  QUÉ PASABA : GET / no filtraba por organization_id. Un propietario podía
               ver citas de pacientes de otras organizaciones si adivinar IDs.
  QUÉ SE HIZO: Añadida condición b.organization_id = :orgId al WHERE.

[BUG-PORTAL-APPOINTMENTS-TOCTOU] services/portal/src/routes/portal.appointments.routes.js
  QUÉ PASABA : PATCH /:id/cancel hacía un SELECT para verificar el status y
               luego un UPDATE separado. Entre ambas operaciones, otro proceso
               podía cambiar el status, permitiendo cancelar citas ya
               completadas o en curso.
  QUÉ SE HIZO: El UPDATE incluye AND status IN ('requested','confirmed') en
               el WHERE. Si affectedRows = 0 se retorna 409 Conflict.

[BUG-006-PORTAL] services/portal/src/routes/portal.profile.routes.js
  QUÉ PASABA : El endpoint PUT /password no tenía rate limiting. Un atacante
               con el token de sesión vigente podía intentar cambios de
               contraseña por fuerza bruta sin restricción.
  QUÉ SE HIZO: Rate limiter de 5 intentos/hora aplicado a PUT /password.

[BUG-016-PORTAL] services/portal/src/routes/portal.profile.routes.js
  QUÉ PASABA : Tras cambiar la contraseña, las sesiones activas del portal
               no se invalidaban. Cualquiera con un refresh token robado
               anterior al cambio podía seguir renovando sesiones
               indefinidamente.
  QUÉ SE HIZO: Después del UPDATE de contraseña se ejecuta DELETE FROM
               portal_sessions WHERE client_id = :id, revocando todos los
               refresh tokens del propietario.

[BUG-007-PORTAL] services/portal/src/routes/portal.fcm.routes.js
  QUÉ PASABA : El registro de token FCM usaba ON DUPLICATE KEY UPDATE
               user_id = :uid, permitiendo que un usuario registrara un token
               FCM que pertenecía a otro usuario y recibiera sus notificaciones
               push.
  QUÉ SE HIZO: Antes de insertar se hace DELETE del token si pertenece a un
               usuario diferente. El ON DUPLICATE KEY UPDATE ya no modifica
               user_id, solo actualiza is_active y last_used_at.

[BUG-014-PORTAL] services/portal/src/routes/portal.fcm.routes.js
  QUÉ PASABA : El nombre del topic FCM se construía como `owner_${clientId}`
               sin sanitizar. Si clientId contuviera caracteres especiales
               (por un bug o manipulación), el topic podría ser inválido o
               permitir suscribirse a topics de otros usuarios.
  QUÉ SE HIZO: El nombre del topic se sanitiza con replace(/[^a-zA-Z0-9_.-]/g,
               '_') antes de llamar a fcm.subscribeToTopic().

[BUG-008-PORTAL] services/portal/src/routes/portal.telemedicine.routes.js
  QUÉ PASABA : El campo meeting_url (URL de la sala WebRTC) se devolvía para
               todas las sesiones de telemedicina, incluyendo las ya
               completadas o canceladas. Un propietario podía obtener URLs de
               salas pasadas e intentar acceder a grabaciones o metadatos.
  QUÉ SE HIZO: meeting_url solo se devuelve cuando ts.status IN
               ('in_progress', 'ready', 'confirmed'). Para otros estados
               el campo es NULL.

[BUG-010-PORTAL] portal.appointments.routes.js + portal.profile.routes.js
  QUÉ PASABA : Los campos de texto libre (reason, notes, address, city,
               firstName, lastName, phone) no tenían validación de longitud
               máxima. Un atacante podía enviar strings de MB en esos campos,
               causando almacenamiento excesivo o errores de truncación
               silenciosa en MySQL.
  QUÉ SE HIZO: Límites añadidos vía express-validator:
               reason ≤ 500, notes ≤ 1000, firstName/lastName ≤ 100,
               phone ≤ 30, address ≤ 300, city ≤ 100.

[BUG-PORTAL-017] services/portal/src/portal.common.js — Header x-org-id
  QUÉ PASABA : publishPortalEvent usaba req.headers['x-org-id'] como fallback
               para obtener el orgId del evento. Este header puede ser
               falsificado por cualquier cliente.
  QUÉ SE HIZO: Eliminado el fallback. orgId proviene exclusivamente de
               req.owner?.orgId (extraído del JWT verificado).

[BUG-PORTAL-JSON-LIMIT] services/portal/src/index.js
  QUÉ PASABA : El límite de body JSON del portal era 5 MB, exageradamente
               alto para una API que solo necesita unos pocos KB por request.
               Facilitaba ataques de DoS por cuerpos grandes.
  QUÉ SE HIZO: jsonLimit reducido de '5mb' a '100kb'.

SECCIÓN 15 — LAB / IMAGING (services/lab-imaging)
────────────────────────────────────────────────────────────────────────────────

[BUG-2] services/lab-imaging/src/routes/imaging.write.routes.js
  QUÉ PASABA : La generación del número de orden de imágenes leía el último

  QUÉ PASABA : Igual que BUG-2 pero en órdenes de patología. El loop de

  QUÉ SE HIZO: Transacción con FOR UPDATE en toda la operación incluyendo

[BUG-9] imaging.read.routes.js / pathology.read.routes.js /
         surgery.read.routes.js / hospitalization.read.routes.js
  QUÉ PASABA : Los parámetros de paginación limit y page no tenían validación.
               Un cliente podía enviar limit=1000000 y obtener toda la base
               de datos en una sola respuesta, exfiltrando datos masivamente.
  QUÉ SE HIZO: En los 4 archivos: limit = Math.min(Math.max(parseInt(limit),
               1), 100). Máximo 100 resultados por página.

               inválidos retornan null.

[BUG-GW-12] gateway/src/config.js — body limit sin allowlist (OOM potencial)
  QUÉ PASABA : JSON_BODY_LIMIT sin validación. Un valor de entorno como "999gb"
               causaría OOM en el proceso.
  QUÉ SE HIZO: Validación contra Set de valores permitidos: 100kb, 256kb, 512kb,
               1mb, 2mb, 5mb. Valor inválido cae al default 512kb.

[BUG-GW-13] gateway/src/routes/registries/patients.registry.js — IDOR multi-tenant
  QUÉ PASABA : Rutas species, breeds, branches, clients/signatures/* no tenían
               tenantMismatchGuard. Un token de tenant A podía acceder a datos de
               tenant B.
  QUÉ SE HIZO: Añadido tenantMismatchGuard en todas esas rutas.

[BUG-GW-14] gateway/src/routes/registries/platform.registry.js — info disclosure de infra
  QUÉ PASABA : GET health/services y GET platform/services solo requerían
               authMiddleware. Cualquier usuario (rol viewer) podía ver el estado
               de todos los circuit breakers, servicios caídos y topología interna.
  QUÉ SE HIZO: Añadido requireGatewayPerm('platform:read') — solo admins/superadmins.

[BUG-GW-15] gateway/src/routes/registries/auth.registry.js — path traversal en reescritura de URL
  QUÉ PASABA : La regex /^\/api\/v[12]\/auth/ sin ancla de fin coincidía con URLs
               como /api/v1/auth@evil.com/path, dejando @evil.com/path como path
               reescrito hacia el proxy.
  QUÉ SE HIZO: Regex cambiada a /^\/api\/v[12]\/auth(?=\/|$|\?)/ con lookahead que
               exige /, fin de string o ? después de auth.
